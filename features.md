# Selti v2 — Функциональные требования

> Архитектурное решение. Все фичи описаны на языке бизнеса, без кода.
> Дата: 2026-08-14

---

## 1. Обзор системы

**Selti** — это семантическая память для ИИ-агентов. Хранит знания, находит похожие, обновляет устаревшие.

**Текущее состояние:**
- ~184 гранулы знаний (code_knowledge, project_meta, dialogue_insights, user_facts)
- PostgreSQL (метаданные) + Qdrant (вектора) + Redis (кеш)
- Зависимость от opencode/akame для создания гранул
- Простой search по similarity
- Забывание = удаление

**Целевое состояние:**
- Независимая грануляция (без opencode)
- Git для знаний (каждое изменение = версия)
- Жизненный цикл без удаления (hot → warm → cold)
- Автоматическое обновление устаревших знаний

## 2. Фичи

### F1: Versioned Memories (Git для знаний)

**Суть:** Каждое изменение гранулы сохраняется как отдельная версия. Старая версия не удаляется — уходит в историю.

**Аналогия:** Git commit. Каждое обновление = коммит. HEAD = актуальная версия.

**Как работает:**

1. При создании гранулы автоматически создаётся первая версия (v1). Гранула получает указатель на эту версию как "HEAD".

2. При обновлении гранулы старая версия не перезаписывается. Вместо этого создаётся новая версия (v2, v3, v4...). HEAD переключается на новую. Старая остаётся в истории.

3. Каждая версия хранит: контент, метаданные, важность, тип изменения (create/update/rollback), причину изменения, ссылку на предыдущую версию.

4. При поиске система возвращает **только HEAD** — актуальную версию. История доступна отдельно.

**Поток данных:**

```
Запрос на обновление
    ↓
Получение текущей HEAD версии
    ↓
Создание новой версии в истории
    ↓
Обновление HEAD в основной таблице
    ↓
Пересчёт эмбеддинга
    ↓
Обновление в Qdrant
```

**Диаграмма:**

```
┌─────────────────────────────────────────────────┐
│              Version Chain                       │
│                                                  │
│  v1 (create) ──→ v2 (update) ──→ v3 (HEAD)     │
│     │                │                │          │
│     └─ content A     └─ content B     └─ content C│
│     └─ 2026-01-01     └─ 2026-03-15     └─ 2026-08-14│
│                                                  │
│  History ← ← ← ← ← ← ← ← ← ← ← ← HEAD     │
└─────────────────────────────────────────────────┘
```

**Что можно делать:**
- Посмотреть всю историю изменений гранулы
- Сравнить две версии (diff)
- Откатить к предыдущей версии
- Увидеть временную шкалу всех изменений

### F2: Storage Tiering (горячее/тёплое/холодное)

**Суть:** Гранулы не удаляются. Только меняют "температуру" хранения в зависимости от частоты обращений.

**Аналогия:** Библиотека. Часто берут — на видном месте. Редко — в подсобку. Очень редко — в архив.

**Уровни:**

| Уровень | Где хранится | Поиск | Когда |
|---------|-------------|-------|-------|
| **Hot** | PostgreSQL + Qdrant | Векторный + SQL | < 30 дней с последнего обращения |
| **Warm** | Только PostgreSQL | SQL FTS | 30–180 дней |
| **Cold** | PostgreSQL (сжатый JSONB) | Ручной запрос | > 180 дней |
| **Frozen** | PostgreSQL + Qdrant | Векторный | Ручная заморозка (никогда не стареет) |

**Как работает:**

1. При обращении к грануле (search, get) она автоматически "прогревается" — переводится в hot. Если была warm — пересчитывается эмбеддинг и загружается в Qdrant. Если была cold — распаковывается контент.

2. Каждую ночь система проверяет: какие гранулы не запрашивались больше 30 дней? Они переводятся из hot в warm. Из warm удаляются вектора из Qdrant.

3. Раз в сутки: гранулы старше 180 дней переводятся из warm в cold. Контент сжимается.

4. Frozen — особый статус. Гранулы, помеченные как критически важные, не переходят между уровнями. Они всегда hot.

**Поток данных:**

```
Пользователь ищет гранулу
    ↓
Гранула найдена в warm (векторов нет)
    ↓
Пересчёт эмбеддинга
    ↓
Загрузка в Qdrant
    ↓
Перевод в hot
    ↓
Возврат результата
```

**Диаграмма переходов:**

```
                    ┌──────────┐
                    │  Frozen  │
                    │ (никогда │
                    │ не меняется)│
                    └──────────┘
                         ↑ ручная заморозка

┌──────┐  30 дней  ┌──────┐  180 дней  ┌──────┐
│ Hot  │ ────────→ │ Warm │ ──────────→ │ Cold │
│ PG+  │           │ PG   │            │ PG   │
│Qdrant│ ←──────── │ (FTS)│ ←───────── │(сжат)│
└──────┘ обращение └──────┘  обращение └──────┘
```

### F3: Granulation Pipeline (независимая грануляция)

**Суть:** Создание гранул знаний из любых данных — диалогов, документов, кода — прямо в selti. Без зависимости от opencode.

**Аналогия:** Пищеварительная система. Проглатываем сырьё → перевариваем → усваиваем полезное → отбрасываем мусор.

**Как работает:**

1. На вход подаются любые данные: текст диалога, markdown-документ, исходный код, ручной ввод.

2. Адаптер конвертирует данные в единый формат. Диалог — в текст с ролями. Код — в текст с языком. Документ — как есть.

3. LLM анализирует текст и извлекает из него факты. Каждый факт — отдельная гранула с содержимым, типом, важностью и связями.

4. Валидатор проверяет качество: длина контента, namespace, тип сущности, важность. Мусор отбрасывается.

5. Дедупликация: точное совпадение (SHA256) + семантическое (cosine). Если гранула уже есть — пропускается или обновляется.

6. Гранула сохраняется в базу с первой версией (v1).

**Поток данных:**

```
Входные данные (диалог/документ/код)
    ↓
Адаптер → единый формат
    ↓
LLM → извлечение фактов
    ↓
Валидатор → отбраковка мусора
    ↓
Дедупликация → проверка на дубли
    ↓
Сохранение → v1 в историю
    ↓
Эмбеддинг → в Qdrant
```

**Диаграмма:**

```
┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
│  Диалог    │  │  Документ  │  │    Код     │  │  Ручной    │
│  opencode  │  │  markdown  │  │  python/js │  │   ввод     │
└─────┬──────┘  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
      │               │               │               │
      └───────────────┼───────────────┼───────────────┘
                      ↓
              ┌───────────────┐
              │   Адаптер     │
              │  (Strategy)   │
              └───────┬───────┘
                      ↓
              ┌───────────────┐
              │  LLM Extract  │
              │  (API call)   │
              └───────┬───────┘
                      ↓
              ┌───────────────┐
              │  Validator    │
              │  (качество)   │
              └───────┬───────┘
                      ↓
              ┌───────────────┐
              │  Dedup        │
              │  (SHA256+cos) │
              └───────┬───────┘
                      ↓
              ┌───────────────┐
              │  Store (v1)   │
              │  PG + Qdrant  │
              └───────────────┘
```

### F4: Knowledge Update Pipeline (автообновление)

**Суть:** Система сама находит устаревшие знания и обновляет их. Например, находит гранулы со словом "pgvector" и заменяет на "Qdrant".

**Аналогия:** Редактор encyclopedia. Находит устаревшие статьи, проверяет факты, обновляет текст.

**Как работает:**

1. Есть правила обнаружения. Каждое правило описывает: что искать (ключевые слова), где искать (namespaces), что заменять, как валидировать.

2. Каждые 12 часов система сканирует все гранулы по правилам. Находит те, которые содержат устаревшую информацию.

3. Для каждой найденной гранулы: вычисляется confidence (насколько точно правило сработало), предлагаются замены.

4. Если включён auto-mode — замены применяются batch'ем. Каждая замена создаёт новую версию (не перезапись!). Эмбеддинг пересчитывается.

5. Дополнительно: проверка ссылок на код (существуют ли файлы/классы), проверка SQL-запросов (проходят ли EXPLAIN).

**Поток данных:**

```
Расписание (каждые 12ч)
    ↓
Загрузка правил из БД
    ↓
Для каждого правила:
    ↓
FTS поиск по ключевым словам
    ↓
Найденные гранулы
    ↓
Валидация (код/SQL/regex)
    ↓
Confidence scoring
    ↓
Batch apply replacements
    ↓
Создание новой версии для каждой
    ↓
Пересчёт эмбеддингов
    ↓
Отчёт в audit_log
```

**Диаграмма:**

```
┌─────────────────────────────────────────────────────┐
│              Knowledge Update Pipeline               │
│                                                      │
│  ┌──────────────┐     ┌──────────────┐              │
│  │ StaleRule    │────→│ StaleDetector│              │
│  │ "pgvector"   │     │  (FTS search)│              │
│  └──────────────┘     └──────┬───────┘              │
│                              ↓                       │
│                      ┌──────────────┐               │
│                      │  Validator   │               │
│                      │  (код/SQL)   │               │
│                      └──────┬───────┘               │
│                              ↓                       │
│                      ┌──────────────┐               │
│                      │ UpdateEngine │               │
│                      │ (replacements)│              │
│                      └──────┬───────┘               │
│                              ↓                       │
│                      ┌──────────────┐               │
│                      │ Version Store│               │
│                      │ (new version)│               │
│                      └──────────────┘               │
│                                                      │
└─────────────────────────────────────────────────────┘
```

**Предустановленные правила:**

| Правило | Что ищет | Что заменяет |
|---------|----------|-------------|
| pgvector → Qdrant | pgvector, embedding vector | Qdrant, Qdrant vector |
| Добавление Celery | архитектура без Celery | описание с Celery |
| Невалидные ссылки на код | несуществующие файлы/классы | — (предупреждение) |
| Невалидный SQL | запросы не проходящие EXPLAIN | — (предупреждение) |

### F5: Graph Lifecycle (управление графом)

**Суть:** Граф знаний (связи между гранулами) автоматически чистится: сироты удаляются, слабые связи обрезаются, похожие гранулы объединяются в схемы.

**Аналогия:** Садовник. Подрезает ветки, удаляет сухие, группирует похожие растения.

**Как работает:**

1. **Orphan detection.** Раз в неделю система находит гранулы, у которых нет ни одной связи (ни исходящей, ни входящей). Если гранула старше 90 дней и importance ≤ 1 — она кандидат на удаление.

2. **Graph pruning.** Слабые связи (weight < 0.1), созданные больше года назад, удаляются. Это чистит граф от шума.

3. **Schema merging.** Группы из 3+ похожих гранул (cosine > 0.85) объединяются в "схему" — одну гранулу-обёртку с links "contained_by". Например, 5 гранул про PostgreSQL → 1 Schema: PostgreSQL.

**Поток данных:**

```
Еженедельно (воскресенье 05:00)
    ↓
Orphan detection
    ↓
Гранулы без связей, age > 90д, importance ≤ 1
    ↓
Пометка как deprecated
    ↓
Через 30 дней → удаление

Еженедельно (воскресенье 06:00)
    ↓
Graph pruning
    ↓
Связи weight < 0.1, age > 365 дней
    ↓
Удаление связей

Ежемесячно (1-е число)
    ↓
Schema merging
    ↓
Semantic clustering (cosine > 0.85, ≥3 гранулы)
    ↓
Создание schema granule
    ↓
Re-linking гранул к schema
```

**Диаграмма:**

```
До merge:                    После merge:

┌──────┐  ┌──────┐          ┌──────────────────┐
│ PG:  │  │ PG:  │          │ Schema: PostgreSQL│
│ index│  │ pool │          │  (contains)       │
└──┬───┘  └──┬───┘          └────────┬─────────┘
   │         │                       │
   │         │              ┌────────┼────────┐
   │         │              ↓        ↓        ↓
┌──┴───┐  ┌──┴───┐     ┌──────┐ ┌──────┐ ┌──────┐
│ PG:  │  │ PG:  │     │ PG:  │ │ PG:  │ │ PG:  │
│ migr │  │ FTS  │     │ index│ │ pool │ │ migr │
└──────┘  └──────┘     └──────┘ └──────┘ └──────┘
```

### F6: Interference Detection (обнаружение противоречий)

**Суть:** Когда добавляется или обновляется гранула, система проверяет: не противоречит ли она существующим знаниям?

**Аналогия:** Факт-чекер. Проверяет новую информацию на конфликт с уже известным.

**Как работает:**

1. При добавлении/обновлении гранулы ищутся семантически похожие (cosine > 0.8).

2. Для каждой похожей гранулы LLM проверяет: противоречит ли новая информация старой?

3. Если противоречит — создаётся конфликт с вариантами разрешения:
   - Обновить старую гранулу
   - Пометить старую deprecated
   - Объединить обе
   - Оставить обе (разные контексты)

### F7: Reflection (рефлексия)

**Суть:** Когда накапливается достаточно важных знаний, LLM синтезирует вывод — higher-order insight из нескольких фактов.

**Аналогия:** Учёный, который после серии экспериментов пишет теорию.

**Как работает:**

1. Считается суммарная importance недавних гранул.

2. Если сумма > порога — LLM получает эти гранулы и генерирует insight.

3. Insight сохраняется как гранула с entity_type="reflection" и связями "derived_from" с исходными гранулами.

## 4. Сущности

### 4.1. Гранула (Knowledge Granule)

Основная единица хранения. Каждая гранула — самодостаточный факт.

| Поле | Описание |
|------|----------|
| id | UUID |
| content | Текст факта |
| namespace | Репозиторий: user_facts, code_knowledge, project_meta... |
| entity_type | Тип: module, class, decision, insight, person... |
| entity_name | Имя сущности (если применимо) |
| importance | 1-5 (1=мелочь, 5=критично) |
| storage_tier | hot / warm / cold |
| lifecycle_state | active / stale / frozen / archived / deleted |
| current_version_id | Ссылка на HEAD версию |
| version_count | Сколько версий |

### 4.2. Версия (Version)

Снимок состояния гранулы в 특정ный момент.

| Поле | Описание |
|------|----------|
| id | UUID |
| granule_id | Ссылка на гранулу |
| version_number | 1, 2, 3... |
| content | Текст на момент версии |
| change_type | create / update / rollback / merge |
| change_reason | Почему изменилось |
| parent_version_id | Ссылка на предыдущую версию |
| created_at | Когда создана |
| created_by | Кто создал |

### 4.3. Связь (Relation)

Рёбра графа знаний.

| Поле | Описание |
|------|----------|
| source_id | Гранула-источник |
| target_id | Гранула-цель |
| link_type | depends_on, used_by, extends, implements, contains... |
| weight | 0.0-1.0 (сила связи) |
| description | Описание связи |

### 4.4. Правило KUP (StaleRule)

Описание что считать устаревшим.

| Поле | Описание |
|------|----------|
| id | pgvector-to-qdrant |
| search_keywords | ["pgvector", "embedding vector"] |
| search_namespaces | ["code_knowledge", "project_meta"] |
| replacements | [{"old": "pgvector", "new": "Qdrant"}] |
| validation_type | keyword / code_ref / sql |
| priority | 1-5 |

## 6. Diagram: потоки данных

### 6.1. Создание гранулы

```
Данные ──→ Адаптер ──→ LLM ──→ Валидатор ──→ Дедуп ──→ Store ──→ Qdrant
                              │                │
                              ↓                ↓
                          Отбраковано      Пропущено
                          (мусор)          (дубликат)
```

### 6.2. Поиск

```
Query ──→ Embedding ──→ Qdrant (только HEAD) ──→ Re-ranking ──→ Результат
                                                           │
                                                           ↓
                                                   Обогащение связями
                                                   (relations)
```

### 6.3. Обновление

```
Изменение ──→ create_version() ──→ new HEAD ──→ re-embed ──→ Qdrant
                    │
                    ↓
            History chain
            v1 → v2 → v3 (HEAD)
```

### 6.4. Auto-tiering

```
Nightly ──→ Проверка last_accessed ──→ hot → warm (30 дней)
                                     ──→ warm → cold (180 дней)
                                     ──→ cold → hot (при обращении)
```

### 6.5. KUP scan

```
Scheduled ──→ Правила ──→ FTS поиск ──→ Валидация ──→ Batch update ──→ new versions
```
