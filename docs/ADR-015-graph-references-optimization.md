# ADR-015: Оптимизация связей графа знаний — замена generic `references` на конкретные типы

**Статус:** accepted  
**Автор:** Эна (architect), Тиамат (tech-writer)  
**Дата:** 2026-08-01  
**Связанные ADR:** ADR-010 (новые LinkType), ADR-011 (superseded), ADR-013 (graph-health-tool)

---

## Контекст

### Текущее состояние графа

| Метрика | Значение |
|---------|----------|
| Всего гранул | 2 654 |
| Всего связей | 6 421 |
| `references` | 3 049 (47.7%) |
| `contained_by` | 828 (12.8%) |
| `depends_on` | 457 (7.1%) |
| `implements_adr` | 384 (5.9%) |
| `solves` | 369 (5.7%) |
| `related_to` | 347 (5.4%) |
| `used_by` | 266 (4.1%) |
| `contains` | 219 (3.4%) |
| Остальные | < 2% каждый |

### Проблема

**47.7% всех связей — generic `references`.** Это шум в графе знаний:

- Невозможно отличить «ADR ссылается на код» от «инсайт упоминает модуль»
- Нет семантики: `references` не несёт информации о причине связи
- Auto-linker использует `references` как fallback при confidence 0.75–0.85
- LLM (Тиш) выбирает `references` как «безопасный» тип

### Корневые причины

| # | Причина | Механизм |
|---|---------|----------|
| 1 | Auto-linker fallback | `link-enricher.ts` ставит `references` при confidence 0.75–0.85 |
| 2 | CNLM-матрица | разрешает `references` между всеми namespace |
| 3 | LLM-поведение | Тиш выбирает `references` когда не уверен в конкретном типе |
| 4 | code_knowledge → code_knowledge | матрица `*` (все типы), нет ограничений |

---

## Решение

### 1. Правила замены `references` по парам namespace

#### project_meta → code_knowledge (~800 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| ADR описывает реализацию модуля | `implements_adr` | ADR — архитектурное решение, модуль его реализует |
| ADR ссылается на существующий код как пример | `references` | Остаётся — это действительно ссылка |
| ADR решает проблему в коде | `solves` | ADR решает конкретную проблему |
| ADR мотивирует изменение кода | `motivates` | Мягкая каузальность |

#### dialogue_insights → code_knowledge (~600 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| Инсайт решает проблему кода | `solves` | Инсайт — решение, код — проблема |
| Инсайт извлечён из обсуждения кода | `derived_from` | Provenance: инсайт извлечён из контекста кода |
| Инсайт упоминает модуль/класс | `references` | Остаётся — упоминание |
| Инсайт мотивирует изменение | `motivates` | Мягкая каузальность |

#### user_facts → code_knowledge (~200 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| Факт мотивирует архитектурное решение | `motivates` | Предпочтение мотивирует ADR |
| Факт извлечён из обсуждения кода | `derived_from` | Provenance |
| Факт упоминает технологию/модуль | `references` | Остаётся — упоминание |

#### project_meta → dialogue_insights (~150 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| ADR informed_by инсайт | `informed_by` | Пассивный залог |
| Инсайт ссылается на ADR | `references` | Остаётся — ссылка |

#### dialogue_insights → project_meta (~100 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| Инсайт мотивирует ADR | `motivates` | Мягкая каузальность |
| Инсайт informed_by ADR | `informed_by` | Пассивный залог |

#### user_facts → project_meta (~80 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| Факт мотивирует ADR | `motivates` | Предпочтение мотивирует решение |
| Факт извлечён из ADR | `derived_from` | Provenance |

#### code_knowledge → code_knowledge (~1000 ссылок)

| Исходный контекст | Замена на | Обоснование |
|---|---|---|
| Модуль зависит от модуля | `depends_on` | Зависимость импортов |
| Модуль использует модуль | `used_by` | Использование |
| Модуль вызывает функцию | `calls` | Вызов |
| Модуль тестирует модуль | `tested_by` | Тестирование |
| Класс расширяет класс | `extends` | Наследование |
| Класс реализует интерфейс | `implements` | Реализация |
| Модуль содержит класс/функцию | `contains` | Вложенность |

### 2. Изменения в auto-linker (link-enricher.ts)

**Было:**
```typescript
if (confidence >= 0.85) {
  // конкретный тип
} else if (confidence >= 0.75) {
  linkType = 'references'; // FALLBACK — слишком много шума
}
```

**Стало:**
```typescript
if (confidence >= 0.90) {
  // конкретный тип (поднят порог)
} else if (confidence >= 0.85) {
  // конкретный тип с более низким порогом
} else if (confidence >= 0.80) {
  // fallback: related_to вместо references (менее generic)
} else {
  // не ставим связь — слишком низкий confidence
}
```

### 3. Изменения в CNLM-матрице

**Было:**
- `code_knowledge → code_knowledge`: `*` (все типы)
- `references` разрешён везде

**Стало:**
- Запретить `references` как fallback для определённых пар:
  - `project_meta → code_knowledge`: `implements_adr`, `solves`, `motivates` (не `references`)
  - `dialogue_insights → code_knowledge`: `solves`, `derived_from`, `motivates` (не `references`)
  - `user_facts → code_knowledge`: `motivates`, `derived_from` (не `references`)
- Разрешить `references` только:
  - Внутри namespace (`code_knowledge → code_knowledge`)
  - Для упоминаний (когда нет конкретной семантики)

### 4. Изменения в промпте Тиши

**Было:**
```
Выбирай тип связи из списка. Если не уверен — используй references.
```

**Стало:**
```
Выбирай конкретный тип связи. references — ТОЛЬКО для упоминаний без семантики.
Приоритет: depends_on > solves > implements_adr > motivates > related_to > references.

Правила:
- Если source — ADR, а target — модуль → implements_adr
- Если source — инсайт, а target — проблема → solves
- Если source — факт, а target — решение → motivates
- Если source — инсайт, а target — ADR → informed_by
- Если нет конкретной семантики → related_to (не references!)
- references — только когда реально нет другого варианта
```

## Миграция

### Этап 1: Анализ (1–2 часа)

1. Выбрать 100 случайных `references`-связей
2. Проанализировать контекст source/target
3. Определить паттерны замены

### Этап 2: Правила замены (30 минут)

1. Записать правила в CNLM-матрицу
2. Обновить промпт Тиши
3. Изменить auto-linker

### Этап 3: Массовая замена (1–2 часа)

1. Запустить скрипт миграции
2. Заменить `references` на конкретные типы по правилам
3. Проверить целостность графа

### Этап 4: Валидация (30 минут)

1. Проверить что все связи валидны по CNLM
2. Проверить что нет broken links
3. Проверить метрики: доля `references` должна быть < 20%

## Ожидаемые результаты

| Метрика | До | После |
|---|---|---|
| `references` | 47.7% (3 049) | < 20% (~600) |
| `implements_adr` | 5.9% (384) | ~12% (~800) |
| `solves` | 5.7% (369) | ~10% (~650) |
| `motivates` | 0.4% (27) | ~3% (~200) |
| `derived_from` | 0.1% (4) | ~2% (~130) |
| `related_to` | 5.4% (347) | ~8% (~520) |

### Целевое распределение (после оптимизации)

- `references`: < 20% — только упоминания без семантики
- `depends_on`: 7–10% — зависимости кода
- `implements_adr`: 10–12% — ADR → реализация
- `solves`: 8–10% — решение проблем
- `related_to`: 6–8% — общая связанность
- `contained_by`: 10–15% — вложенность
- Остальные: 15–20% — конкретные семантические типы

## Риски

| # | Риск | Mitigation |
|---|------|------------|
| 1 | Неверные замены — автоматическая замена может поставить неверный тип | Валидация после замены, ручная проверка выборки |
| 2 | Потеря информации — `references` более generic | `references` остаётся для упоминаний |
| 3 | Сложность миграции — много связей для обработки | Поэтапная миграция, начиная с самых частых пар |

---

## Альтернативы

| # | Альтернатива | Решение |
|---|-------------|---------|
| 1 | Оставить как есть — `references` допустимый generic тип | Отклонено: шум в графе мешает анализу и навигации |
| 2 | Удалить все `references` — полная чистка | Отклонено: потеря информации, некоторые связи действительно generic |
| 3 | Добавить новые типы — расширить LinkType | Частично принято: новые типы уже добавлены (ADR-010), нужно использовать их |
