# SETTINGS — система конфигурации selti

Как устроена конфигурация: три слоя значений, env-блокировка, горячее
применение без рестарта, REST API, профили и процедура добавления новой
настройки.

Полный перечень всех ключей с русскими названиями и тултипами —
[docs/SETTINGS_REGISTRY.md](SETTINGS_REGISTRY.md) (единственный источник
истины по составу: 97 runtime-ключей, 11 групп, фундамент env-only).

Экран управления — **/ui/settings** (раздел «Конфигурация»): настройки с
русскими названиями, разбивка по темам, подсказка «?» у каждой настройки.

---

## 1. Обзор: три слоя

Резолв значения любого runtime-ключа — строго в этом порядке:

```
1. env/compose (явно заданный)  — приоритет высший, применение рестартом
2. БД app_settings.value        — runtime-слой, меняется без рестарта
3. Дефолт из config.py          — база, значения сидинга = им
```

| Слой | Где живёт | Как меняется | Когда применяется |
|---|---|---|---|
| env/compose | `.env`, `docker-compose.yml` | правка файла + рестарт контейнера | рестарт процесса |
| БД | таблица `app_settings` (миграция 027) | PUT `/api/settings` или экран /ui/settings | налету (hot-reload) |
| Дефолт | поля `memory_server/config.py` | только правкой кода | всегда в основе |

Зачем так: **единая правда в БД** — оператор крутит поведение системы из UI,
без релиза и рестарта; **аварийный люк в compose** — ключевое значение можно
жёстко зафиксировать на уровне окружения, и никакая ручка в UI его не
перебьёт. Сидинг миграции копирует дефолты `config.py` бит-в-бит, поэтому
«свежая» система неотличима от прежней.

API на каждый ключ отдаёт `effective_source: "env" | "db" | "default"` —
откуда действует значение прямо сейчас.

## 2. Env-блокировка

Runtime-ключ, явно заданный в env/compose, **жёстко блокируется**: это
блокировка, а не предупреждение.

**Как детектируется «задано в env»:**

- основной механизм — pydantic `Settings.model_fields_set`: множество полей,
  реально заданных при создании `Settings`. Оно точно отличает «задано в env»
  от «совпало с дефолтом» — совпадение значения не считается оверрайдом;
- для ключей **без поля в `Settings`** (например, `schedule.*`) — csv-переменная
  `RUNTIME_ENV_OVERRIDES`: перечисленные в ней ключи читаются из env-переменной
  с именем `KEY.TO.UPPER()` и парсятся по типу реестра.

Оба механизма сходятся в `compute_env_overrides()` (`settings_store.py`);
детекция выполняется **один раз за жизнь процесса** — `model_fields_set`
фиксирован на старте.

**Что блокируется:** env-ключ нельзя записать (`PUT`), сбросить (`reset`,
в том числе через `reset-all`) и применить профилем — все пути отвечают
**409**. В UI поле рендерится read-only с бейджем «Управляется через
.env/compose».

**Разблокировка:** выпилить переменную из compose/.env и рестартнуть
контейнер. По-другому — никак.

**Защита от опечаток:** env-ключ, которого нет ни в runtime-реестре, ни в
списке фундамента, → `WARN` в лог и игнор (процесс не падает).

**Фундамент — env-only, всегда.** Секреты (`DATABASE_URL`, `API_KEY`,
`EMBEDDING_API_KEY`, `QDRANT_API_KEY`, `LINKER_LLM_API_KEY`, …) и
инфраструктура (адреса, порты, пулы) в `app_settings` **не сидируются
никогда**: через `/api/settings` не отдаётся ни значений, ни метаданных.
Полный перечень фундамента — §3 реестра.

## 3. Как это работает внутри

### RuntimeConfig — снапшот в памяти (`runtime_config.py`)

Каждый процесс (web, worker, beat) держит **in-memory снапшот** effective-значений.
`runtime.get("key")` — sync-словарный lookup: **ноль IO на горячем пути**.
Резолв снапшота: дефолты ← БД-переопределения ← env-блокировки.

Актуализация снапшота — два механизма:

1. **Мгновенная инвалидация:** триггер миграции 027 на любой
   INSERT/UPDATE/DELETE в `app_settings` шлёт `pg_notify('settings_changed', key)`.
   Каждый процесс держит выделенное LISTEN-соединение (пул его не занимает —
   acquire/release переключает соединения и рвёт подписку) и по событию
   запускает фоновый полный refresh. Полный, а не точечный: 97 строк дёшевы,
   а cross-field-инварианты (инвариант линкера) требуют консистентный снапшот.
2. **TTL-страховка 60 секунд:** если снапшот старше 60 с (например, LISTEN-канал
   умер тихо), очередной `get()` запускает фоновую догрузку — следующее чтение
   увидит свежее значение. Keep-alive LISTEN-соединения — ping каждые 30 с,
   реконнект через 5 с.

**Поведение при недоступной БД:** refresh ловит исключение → `WARN` в лог,
снапшот остаётся прежним. При старте без БД процесс поднимается на дефолтах
(+ env-оверрайды) с `WARN` — не падает.

Для стартовых кодов без event loop (`celeryd_init`, `beat_init`) есть
sync-путь `load_effective_values_sync()`: одноразовое соединение с короткими
таймаутами (5 с), чтобы лежащая БД не вешала старт.

### RuntimeScheduler — beat-расписания (`celery_app.py`)

- Beat-планировщик `RuntimeScheduler` **перечитывает schedule-ключи каждые
  30 секунд** (на тике, `sync_every = 30.0`); при изменении — полная пересборка
  записей расписания: новое расписание стартует налету, без рестарта
  контейнера beat (паттерн django-celery-beat).
- Значение битое/нечитаемое → дефолт + `WARN`.
- БД недоступна → последние прочитанные значения сохраняются (sync-путь не бросает).

### Применение настроек воркера (группа `celery`)

- `celery_worker_concurrency` — **налету**: запись значения через API шлёт
  broadcast `pool_grow` / `pool_shrink` живым воркерам. Best-effort: воркер
  офлайн — применит при своём рестарте (`celeryd_init` читает БД на старте).
- `max_tasks_per_child` / `max_memory_per_child` и остальные 8 ключей группы —
  **только рестарт** воркера: семантика per-child (счётчики и RSS-лимит живут
  в каждом чилде с момента его рождения), приложение нового значения на лету
  не определено.
- Группа `linker_llm_*` (4 ключа) — рестарт: пересоздание LLM-клиента.
- Итого `requires_restart` = 25 ключей: celery 8 (concurrency — исключение),
  schedule 13, linker_llm 4. Значение в БД меняется сразу, эффект — после
  рестарта процесса; UI показывает бейдж «нужен рестарт».

Пост-запись через API: снапшот web-процесса обновляется сразу, остальные
процессы получают `pg_notify`.

## 4. REST API

Префикс `/api/settings`. Контракт реализует `memory_server/api/settings.py`;
схема ключа — реестр кода (`settings_store.REGISTRY`), значения и метаданные
сидинга — БД.

| Метод и путь | Назначение | Успех |
|---|---|---|
| `GET /api/settings` | Все 97 ключей + список групп | `{"settings": [SettingOut…], "groups": [{"key", "title_ru"}…]}` |
| `GET /api/settings/{key}` | Один ключ | `SettingOut` |
| `PUT /api/settings/{key}` | Записать значение | `SettingOut` (обновлённый) |
| `POST /api/settings/{key}/reset` | Сброс к дефолту (строка удаляется из БД) | `SettingOut` |
| `POST /api/settings/reset-all` | Сброс всех БД-переопределений | `{"reset": [ключи]}` |
| `GET /api/settings/profiles` | Список профилей | `{"profiles": [ProfileOut…]}` |
| `POST /api/settings/profiles` | Создать профиль (снапшот текущих значений) | `ProfileOut`, `201` |
| `PUT /api/settings/profiles/{id}` | Перезаписать снапшот профиля текущими значениями | `ProfileOut` |
| `DELETE /api/settings/profiles/{id}` | Удалить профиль | `{"deleted": id}` |
| `POST /api/settings/profiles/{id}/apply` | Применить профиль атомарно | `{"applied": […], "skipped_env": […]}` |

Тела запросов: `PUT {key}` — `{"value": …, "confirm": false}`; `reset` /
`reset-all` / `apply` — `{"confirm": false}`; создание профиля —
`{"name", "description?"}`.

`SettingOut` (на каждый ключ): `key`, `group`, `value_type`, `widget`,
`value`, `db_value`, `default_value`, `effective_source`,
`differs_from_default`, `is_env_locked`, `is_dangerous`, `requires_restart`,
`min_value`, `max_value`, `enum_values`, `title_ru`, `description_ru`,
`updated_at`, `updated_by`.

**Ошибки:**

| Код | Когда | Тело |
|---|---|---|
| `400` | Значение не прошло валидацию схемы (тип, min/max, enum, json-подсхемы, инвариант линкера) | `{"message": str, "errors": [str…]}` |
| `409` | Опасная операция без `confirm: true` | `{"message": str, "keys": [ключи]}` |
| `409` | Ключ заблокирован env/compose | `{"message": str}` |
| `404` | Неизвестный ключ / профиль не найден | `detail: str` |
| `503` | Таблица `app_settings` недоступна | `detail: str` |

Техническая деталь маршрутизации: статические префиксы (`/profiles`,
`/reset-all`) объявлены **до** параметрического `/{key}` — иначе FastAPI
сматчит `"profiles"` как имя ключа.

## 5. Профили настроек

Профиль — **снапшот всех 97 runtime-ключей** одним JSONB-блобом
(`app_settings_profiles.values`, миграция 027). Построчная таблица
отклонена: профиль читается и пишется всегда целиком, diff «профиль vs
текущее» — одно jsonb-сравнение.

- **Встроенный профиль «Заводские настройки»** (`name=default`,
  `is_builtin=true`) сидируется миграцией 027 каноническими дефолтами всех
  97 ключей. Он read-only: изменить или удалить его нельзя (409).
- **Пользовательские профили** создаются снапшотом *текущих* effective-значений
  (имя уникально, дубликат → 409). Перезапись снапшота — PUT-эндпоинтом.
- **Apply атомарен:** вся валидация (схема, dangerous-confirm, инвариант
  линкера) выполняется *до* транзакции, записи — в одной транзакции. Обрыва —
  не бывает: либо всё применилось, либо ничего.
- **Env-ключи пропускаются с отчётом:** env жёстко сильнее профиля, поэтому
  такие ключи не трогаются и возвращаются в `skipped_env` ответа.

Типовой сценарий: настроить систему в UI → сохранить профиль →
экспериментировать → apply профиля возвращает к проверенной конфигурации;
«Заводские настройки» — возврат к дефолтам `config.py` одним кликом
(эквивалент `reset-all`, но с теми же правилами confirm).

## 6. Опасные настройки

Ключи с флагом `is_dangerous` (8 штук) — те, чья цена ошибки высока:
физическое удаление знаний, массовые боевые кампании, мастер-выключатели
подсистем.

| Ключ | Группа | Что делает |
|---|---|---|
| `dedup_enabled` | dedup | Выключение дедупликации допускает дубли знаний |
| `gc_purge_enabled` | lifecycle | Мастер-кран физического удаления (hard delete) |
| `gc_mode` | lifecycle | Режим GC: `disabled` / `soft` / `hard` |
| `gc_retention_days` | lifecycle | Срок хранения версий до физического удаления |
| `linker_enabled` | linker | Мастер-выключатель построения новых связей |
| `linker_reconciler_dry_run` | linker | Боевой резолв «висячих» ссылок вместо отчёта |
| `edge_lifecycle_enabled` | edge | Мастер-флаг жизни рёбер (затухание/отсечение) |
| `edge_prune_dry_run` | edge | Боевое отсечение рёбер вместо отчёта |

**Поведение:** запись значения **и** сброс к дефолту (включая групповой
`reset-all` по группе с опасными ключами и apply профиля, содержащего
опасные ключи) требуют явного `confirm: true` — иначе **409** со списком
затронутых ключей (ничего не меняется). UI показывает бейдж «опасно» и
модалку подтверждения с человеческим текстом последствий.

**Инвариант линкера** (проверяется при каждой записи на итоговом состоянии):
для каждого namespace

```
linker_synonym_threshold < linker_verdict_threshold <= dedup_thresholds[ns]
```

Слои близости не пересекаются: ниже порога синонимии — тишина, между
синонимией и вердиктом — auto-связи L1a, между вердиктом и дедупом — только
явный вердикт (LLM или человек), выше — зона дедупликации. Равенство
`verdict == dedup_thresholds[ns]` допустимо: L2-зона namespace вырождается в
пустую (пары уходят сразу в дедуп) — на этих дефолтах система и живёт
(0.85 == 0.85 для `dialogue_insights`). Нарушение инварианта → 400.

## 7. Чек-лист: добавить новую настройку

1. **Поле в `memory_server/config.py`** с дефолтом и комментарием-rationale
   (код — английский, комментарий — русский).
2. **Строка `SettingSpec`** в `settings_store.py` (`_build_registry`): ключ,
   тип, группа, ограничения min/max/enum, флаги `dangerous` /
   `requires_restart`, виджет.
3. **Русские тексты**: строка сидинга по формату миграции 027
   (`INSERT … ON CONFLICT (key) DO NOTHING`, отдельной миграцией по образцу
   027) **и/или** запись в [docs/SETTINGS_REGISTRY.md](SETTINGS_REGISTRY.md)
   §2 с `title_ru`/`description_ru` — для следующей миграции. Названия и
   тултипы живут только здесь — из них строится UI.
4. **Виджет подбирается автоматически** — фронт рендерит по полю `widget`,
   выбор при регистрации ключа:

   | Виджет | Для чего |
   |---|---|
   | `switch` | bool-флаги |
   | `slider_number` | int/float с ограниченным диапазоном (ползунок) |
   | `number` | int/float без смысла в ползунке |
   | `combobox` | str-enum (`enum_values`) |
   | `checkboxes` | json-массив из фиксированного набора значений |
   | `kv_table` | json-объект namespace → число (с обязательным `default`) |
   | `text` | свободный текст / JSON-редактор (schedule-ключи) |

5. **Потребитель читает `runtime.get("key")`** — не поле `Settings` напрямую:
   только так работает hot-reload. В FastAPI-валидаторах (`Query(…)`)
   значение не замораживать — резолвить внутри хендлера.
6. **Тест на согласованность трёх реестров:**
   [tests/test_settings_registry_sync.py](../tests/test_settings_registry_sync.py)
   сверяет `settings_store.REGISTRY` (код), сидинг миграции 027 (БД) и
   документ `docs/SETTINGS_REGISTRY.md` — множество ключей, типы, дефолты,
   min/max, enum, флаги, группы, виджеты, русские тексты. Правка одного
   источника без двух других — красный прогон с точным diff. Для нового
   ключа добавьте его во все три места, и тест подтвердит согласованность;
   для ключа с отложенным сидингом сверка подскажет, чего не хватает.

## 8. История

**До миграции 027** все дефолты жили в `config.py`, часть дублировалась
env-переменными, а изменение любой константы означало правку кода и рестарт:

- `SET statement_timeout = '45s'` был зашит литералом в `db/pool.py`;
- таймаут моста REST→celery (300 с) — литерал в `task_bridge.py`;
- капы API `MAX_SEARCH_LIMIT` / `MAX_GRAPH_DEPTH` — константы `api/web.py`.

**Миграция 027_app_settings.sql** (Нора, 2026-09-23, Ф1) ввела:

- таблицу `app_settings` — 97 runtime-ключей: значение, тип, группа,
  русские title/description, канонический дефолт, min/max/enum, флаги
  `is_dangerous` / `requires_restart`. Решения схемы: значения — JSONB
  (пять типов в одной таблице; типизированные колонки дали бы 5 nullable-пар),
  без CHECK на `group_key` (группы — данные реестра, не доменная модель);
- триггер `trg_app_settings_notify` — атомарное `pg_notify('settings_changed')`
  на INSERT/UPDATE/DELETE (ключ на DELETE — из `OLD.key`: `NEW` не существует);
- таблицу `app_settings_profiles` — профили-снапшоты + builtin `default`;
- сидинг 97 ключей с `ON CONFLICT DO NOTHING` — повторный прогон не перетирает
  ручные правки.

Транспортные константы при этом **не** стали runtime-ключами (вердикт аудита,
§5 реестра): `DB_STATEMENT_TIMEOUT` и `TASK_RESULT_TIMEOUT` переехали в
env-фундамент (`config.py`, поля `db_statement_timeout` / `task_result_timeout`)
— они связаны с транспортными таймаутами и меняются только с деплоем, а
`_MAX_POOL_PER_PROCESS`, `_REDIS_TIMEOUT`, `_LOCAL_HOSTS` и beat-константы
надёжности остались в коде: это не настройки оператора.
